# Jellyfin -> pyrate.media Feature Gap Analysis

Date: 2026-05-11

This analysis surveys user-facing Jellyfin functionality from `references/jellyfin/Jellyfin.Api/Controllers/`, with spot checks in `references/jellyfin/MediaBrowser.Model/`, then compares it to pyrate.media's FastAPI routes in `backend/src/pyrate/api/v1/` and Vue/Quasar surfaces in `frontend/src/`. It intentionally ignores Jellyfin internals, database mechanics, CI, and C# implementation details.

## Implementation Guardrails

This document is a gap analysis, not an instruction to mirror another project's controller/module layout. Every parity item must be implemented as native pyrate functionality.

Before adding or changing code, check whether pyrate already has an owning module, route namespace, model, service, schema, store, or frontend surface for the domain. If an owner exists, extend that owner directly. New files/modules are allowed only when there is no existing pyrate owner for that domain.

Do not add adapter/shim route systems, foreign-product-specific names, uppercase route variants, copied controller names, or duplicate services/models/schemas. Do not introduce routes just to satisfy another client's URL or payload shape. Route and payload names must follow pyrate's existing lowercase, kebab-case/snake_case conventions.

Reference controller names in this document are evidence only. They must not be copied into pyrate module, router, path, payload, schema, service, model, or frontend names.

Concrete ownership defaults for parity work: scheduled-task work extends `backend/src/pyrate/api/v1/tasks.py`; install/setup wizard work extends `backend/src/pyrate/api/v1/install.py` and must not introduce startup-named install routes; list, collection, and playlist work extends the existing list owner `backend/src/pyrate/api/v1/lists.py`; notification dispatch work extends `backend/src/pyrate/services/notification.py`; watch-party work extends the existing party domain. If a future feature appears not to fit one of these owners, document the owner search and decision before creating a new file.

Required pre-merge audit for parity work:

1. Search source and tests for foreign-product names, `compat`, `alias`, uppercase route paths, copied route names, and route modules that duplicate existing pyrate owners.
2. Review `backend/src/pyrate/api/router.py` and every new `backend/src/pyrate/api/v1/*.py` file for ownership. If a route is only a facade over an existing domain, move it into the existing module or remove it.
3. Review new models, schemas, and services against existing pyrate modules. Re-export or shim modules are not allowed.
4. Verify frontend calls use the native pyrate route names and payload shapes.
5. Run focused tests for every touched owner plus the static route/name searches before merge.

Current audit result, 2026-05-11:

- Static source/test scan found no foreign-product names, `scheduled_tasks_compat`, `scheduled_tasks_jellyfin`, `startup_router`, copied user-view/music-genre/notification-dispatch/watch-party files, uppercase backend route paths, or route-alias shims in `backend/src`, `frontend/src`, `backend/tests`, or `frontend/test`.
- Follow-up scan after the latest playback/search/session work again found no copied route modules, uppercase backend route paths, or foreign-product route/payload names. The only `watch_party` filename hit is the pre-existing pyrate party-domain test file; current work did not add a `watch_party.py` module or a duplicate watch-party system.
- Latest owner-integrated follow-up added cast protocol container/transcoding profiles, a native device session contract, include/exclude browse filters, year-list filtering, and subtitle provider match diagnostics in existing pyrate owners only. Static route/name scans remain clean.
- `compat` hits are descriptive pyrate capability text only: Newznab/Torznab compatibility labels, metadata-provider compatibility wording, codec/container compatibility checks, and user codec-compatibility preferences. They are not alternate route systems or shim modules.
- Router ownership review: media adjuncts (`attachments.py`, `chapters.py`, `lyrics.py`, `subtitles.py`, `user_data.py`) mount under `/media`; collection/playlist routes remain in `lists.py`; install wizard routes remain in `install.py`; task routes remain in `tasks.py`; notification dispatch remains in `services/notification.py`; activity dispatch remains in `services/activity_log.py`; cast work remains in `cast.py`; offline work remains in `devices.py`.
- New backend API modules accepted as native owners where pyrate did not already have that domain owner: `activity_logs.py`, `api_keys.py`, `backups.py`, `branding.py`, `cast.py`, `client_logs.py`, `environment.py`, `filters.py`, `localization.py`, `plugins.py`, `quick_connect.py`, `suggestions.py`, `system.py`, and `trailers.py`. These must stay pyrate-named and must not grow compatibility facades.
- New backend models/schemas/services accepted as domain owners only where no existing pyrate owner existed: activity logs, API keys, quick connect, network runtime, subtitle provider adapters, and task event tracking. Existing playback, search, media, library, device, list, task, notification, settings, and user domains must continue to be extended in place.

## Detailed Findings

### Library Types and Browsing

Jellyfin exposes generalized item browsing and user-scoped item browsing through `Jellyfin.Api/Controllers/ItemsController.cs`, with endpoints such as `Items`, `Users/{userId}/Items`, and resume/user-data routes. It also has specialized controllers for movies, TV shows, audio/artists, genres, music genres, persons, studios, years, trailers, user views, and filters: `MoviesController.cs`, `TvShowsController.cs`, `AudioController.cs`, `ArtistsController.cs`, `GenresController.cs`, `MusicGenresController.cs`, `PersonsController.cs`, `StudiosController.cs`, `YearsController.cs`, `TrailersController.cs`, `UserViewsController.cs`, and `FilterController.cs`.

pyrate has a unified `MediaItem` model for movies, shows, seasons, episodes, games, music, artists, albums, songs, books, audiobooks, audiobook chapters, photos, and home videos in `backend/src/pyrate/models/media.py`. Registered library plugins currently cover `MOVIES`, `SHOWS`, `MUSIC`, `GAMES`, `BOOKS`, and `PHOTOS` in `backend/src/pyrate/libraries/__init__.py`; photo/home-video scanning lives in `backend/src/pyrate/libraries/photos.py`; library browsing belongs in the existing library/media route owners rather than a copied user-view route module; trailer read/update APIs live in `backend/src/pyrate/api/v1/media.py`, with permission- and parental-limit-aware top-level trailer browsing in `backend/src/pyrate/api/v1/trailers.py`; API browsing/search/details live in `media.py`. The frontend exposes media lists, detail pages, people, favorites, lists, history, trailers, and search in `frontend/src/router/routes.js`.

Status: **Partial**. pyrate covers many major content types, games, photos/home videos, per-item metadata-backed trailers, and top-level trailer browsing, but Jellyfin's broad filter/view ecosystem still needs more depth. Any future view/filter work must extend native media/library/search/filter owners rather than adding copied controller-shaped route modules.

### Library Management, Scanning, and Refresh

Jellyfin has media folder, physical path, refresh, delete, counts, similar items, and library option endpoints in `Jellyfin.Api/Controllers/LibraryController.cs`; library structure is separately handled by `LibraryStructureController.cs`, and item refresh by `ItemRefreshController.cs`. `MediaBrowser.Model/Configuration/LibraryOptions.cs` and related configuration types show per-library metadata/image/subtitle/trickplay options.

pyrate has library type discovery, plugin UI config, metadata provider discovery, library CRUD, physical path status and folder listing, media-folder validation/attach/detach state, audited primary path migration with old-path retention as a media folder, per-library folder validation policies, per-library metadata/image/subtitle/trickplay options, explicit library scan/refresh endpoints, movie/show/simple library config, naming preview, scoring config, trending import, and external-ID import in `backend/src/pyrate/api/v1/libraries.py`. Actual scan support is implemented through plugin methods such as `scan_library` in `backend/src/pyrate/libraries/movies.py`, `shows.py`, `books.py`, and `audiobooks.py`, with orchestration in `backend/src/pyrate/services/library.py`. Metadata refresh is exposed on media items at `backend/src/pyrate/api/v1/media.py` and implemented in `backend/src/pyrate/services/metadata_refresh.py`.

Status: **Partial**. Core folder inspection, media-folder validation, media-folder attach/detach, audited primary path migration, and configurable folder validation policies exist; deeper library-management polish and specialized Jellyfin behaviors can still be added.

### Playback and Streaming

Jellyfin supports playback negotiation and streaming via `MediaInfoController.cs`, `VideosController.cs`, `AudioController.cs`, `UniversalAudioController.cs`, `DynamicHlsController.cs`, `HlsSegmentController.cs`, `PlaystateController.cs`, `TrickplayController.cs`, and `MediaSegmentsController.cs`. Its model surface includes DLNA profiles, playback info, transcoding info, media sources, trickplay DTOs, and session play methods in `MediaBrowser.Model/Dlna/`, `MediaBrowser.Model/MediaInfo/`, `MediaBrowser.Model/Dto/MediaSourceInfo.cs`, and `MediaBrowser.Model/Session/`.

pyrate has playback session creation, token-backed direct file playback when codec/container negotiation allows native browser playback, read-only playback-info/media-source negotiation with explicit media source selection, explicit client container and bitrate capability handling, play/seek request media-source selection, built-in and settings-backed custom playback profiles, seek, song identification, and problem reporting in `backend/src/pyrate/api/v1/play.py`; HLS playlist/segment/trickplay/audio/book/direct-file stream routes plus token-protected trickplay manifests in `backend/src/pyrate/api/v1/stream.py`; transcoding session status/log cleanup in `backend/src/pyrate/api/v1/sessions.py`; client capability registration in `backend/src/pyrate/api/v1/devices.py`; and stream listing, selectable media-source listing, file reprobe, and file download endpoints in `backend/src/pyrate/api/v1/media.py`. The frontend uses `frontend/src/pages/PlayPage.vue`, `frontend/src/composables/usePlay.js`, `frontend/src/composables/useStreamSwap.js`, `frontend/src/composables/usePlayerControls.js`, `frontend/src/composables/useVideoPlayerEvents.js`, `frontend/src/components/CustomPlayerControls.vue`, `frontend/src/components/StreamInfoDialog.vue`, and `frontend/src/components/AudioPlayer.vue` to preserve selected media sources across seek/audio/quality swaps, send browser codec/container capability hints, load trickplay thumbnails from the stream manifest, and use direct file playback when the backend returns it.

Status: **Partial**. HLS transcoding, player controls, token-backed direct file playback/delivery, direct-play fallback when the transcode codec policy blocks an unnecessary transcode, trickplay sprite manifests with frontend hookup, device capability registration, built-in/custom playback profiles, selectable media-source listing, playback-info decisions, explicit container/bitrate capability negotiation, protocol container/transcoding capability profiles, and profile/device-aware play/seek requests with explicit source selection and direct-play/direct-stream/transcode decisions exist, but Jellyfin-grade DLNA protocol negotiation and broader external-client integration are not yet comparable.

### Subtitles, Audio Tracks, Chapters, Lyrics, Attachments

Jellyfin has subtitle delete/search/download/stream/upload and fallback font APIs in `Jellyfin.Api/Controllers/SubtitleController.cs`, lyrics get/upload/delete/remote search/download APIs in `LyricsController.cs`, video attachment APIs in `VideoAttachmentsController.cs`, and media segment/chapter-like surfaces in `MediaSegmentsController.cs` plus item DTO fields under `MediaBrowser.Model/Dto/`.

pyrate's player UI exposes audio track, subtitle, and quality menus in `frontend/src/components/CustomPlayerControls.vue`, with related composables in `frontend/src/composables/useMediaTracks.js` and stream/file metadata from `backend/src/pyrate/api/v1/media.py`. The stream metadata endpoint includes embedded subtitle streams plus managed/uploaded subtitle tracks, and the frontend can fetch uploaded or URL-backed subtitle text through pyrate's authenticated subtitle content endpoint, convert SRT to WebVTT, and attach it as a Video.js remote text track without relying on third-party CORS. Skip markers and credits are represented by `backend/src/pyrate/api/v1/media_markers.py` and `frontend/src/components/SkipOverlay.vue`; managed subtitle metadata, text upload/content, metadata/network provider search/download APIs, and OpenSubtitles-style nested search response normalization plus API-key-backed download-link resolution are exposed in `backend/src/pyrate/api/v1/subtitles.py` with provider normalization and HTTP JSON adapters in `backend/src/pyrate/services/subtitle_provider.py`; chapter read/update APIs are exposed in `backend/src/pyrate/api/v1/chapters.py`; lyrics read/update/delete plus metadata/network-backed remote search/download APIs with LRCLIB camelCase/snake_case response normalization are exposed in `backend/src/pyrate/api/v1/lyrics.py`, configured through `/api/settings/lyrics`, and displayed from the persistent audio player through `frontend/src/stores/audioPlayer.js` and `frontend/src/components/AudioPlayer.vue`; attachment read/update APIs live in `backend/src/pyrate/api/v1/attachments.py`; and fallback-font/provider settings live in `backend/src/pyrate/api/v1/settings.py`.

Status: **Partial**. Basic local stream-track selection, subtitle metadata management, text subtitle upload/content plus URL-backed subtitle proxying with player-track hookup, metadata-backed and generic HTTP JSON provider search/download, OpenSubtitles search normalization and download-link resolution, chapter APIs, lyrics read/update/delete plus metadata-backed, generic HTTP JSON, and LRCLIB-shaped remote lyrics search/download with provider settings and audio-player display, attachment APIs, player-persisted selected-track preferences, and subtitle fallback-font settings are present, but additional provider-specific integrations can still be deepened.

### Metadata and Artwork

Jellyfin separates metadata identification, remote image lookup, item update, image serving, item refresh, people, genres, studios, years, and provider information across `ItemLookupController.cs`, `RemoteImageController.cs`, `ItemUpdateController.cs`, `ImageController.cs`, `ItemRefreshController.cs`, `PersonsController.cs`, `GenresController.cs`, `StudiosController.cs`, and `YearsController.cs`. `MediaBrowser.Model/Providers/` includes remote search results, external IDs, image provider info, subtitle provider info, lyric provider info, and external URLs.

pyrate has metadata provider config/test/capability routes in `backend/src/pyrate/api/v1/metadata.py`, per-item metadata refresh, audited manual metadata edits, metadata-backed identify/apply, live provider identify search, metadata-backed and live provider remote image search/select with language/neutral filtering, selected remote image proxying, normalized external provider links from stored relationship-backed and extra-data external IDs exposed both in media details and a focused external-links endpoint, normalized person external links for TMDB/homepage metadata, safe external-ID item lookup without async lazy-load failures, client/proxy image transform descriptors, packaged Pillow-backed transforms for uploaded and proxied remote artwork, and audited single/bulk artwork set/clear/upload APIs with local uploaded artwork serving in `backend/src/pyrate/api/v1/media.py`, TMDB/TVDB/IGDB/Spotify/MusicBrainz/OpenLibrary/Shazam providers under `backend/src/pyrate/metadata/`, and normalized refresh/import logic in `backend/src/pyrate/services/metadata_refresh.py`. Media stores common poster/backdrop/cast/external-ID style fields in `backend/src/pyrate/models/media.py` and `backend/src/pyrate/models/person.py`; UI surfaces include `frontend/src/pages/admin/MetadataPage.vue`, `MediaDetailPage.vue` with provider external-link buttons, `PersonPage.vue` with person external-link buttons, and `MediaCastRow.vue`.

Status: **Partial**. Provider-backed import/refresh, audited manual metadata updates, metadata-backed identify/apply, live provider identify search, metadata-backed and live provider remote image search/select with language filtering, selected remote image proxying, normalized media/person external provider links, safe external-ID lookup, audited artwork set/clear/upload, local uploaded artwork serving, transform descriptors, packaged uploaded/remote artwork resizing/transcoding, provider capability flags, and basic years/studios navigation endpoints exist, but deeper provider-specific image semantics remain a gap.

### Users, Auth, Profiles, Permissions, Parental Controls

Jellyfin's user and auth surface includes `UserController.cs`, `QuickConnectController.cs`, `ApiKeyController.cs`, `DevicesController.cs`, `DisplayPreferencesController.cs`, and user policy/configuration models such as `MediaBrowser.Model/Users/UserPolicy.cs` and `MediaBrowser.Model/Configuration/UserConfiguration.cs`. QuickConnect login is visible in `UserController.cs` and `QuickConnectController.cs`, and display preferences include Chromecast-version storage.

pyrate has JWT/OIDC auth, refresh/logout/register/email verification/password reset/me routes in `backend/src/pyrate/api/v1/auth.py`; QuickConnect-style pairing sessions in `backend/src/pyrate/api/v1/quick_connect.py` with authenticated approval UX in `frontend/src/pages/QuickConnectPage.vue`; install/bootstrap in `install.py`; user CRUD/password/preferences/parental control/permission override/stats/invites/friendships plus per-client display preferences including a first-class `chromecast_version` field, remote-access overrides, access schedules, and concrete per-library access reporting in `users.py`; groups and permission aggregation in `groups.py`; invites in `invites.py`; devices in `devices.py`; and schedule/remote-access policy enforcement for HTTP/API-key auth plus WebSocket connections in `backend/src/pyrate/auth/dependencies.py` and `backend/src/pyrate/api/v1/ws.py`. Frontend coverage includes auth pages, QuickConnect approval, install, user settings, admin users/groups/invites/devices in `frontend/src/router/routes.js` and `frontend/src/components/admin/`.

Status: **Partial**. Core account management is strong for a young app and now includes QuickConnect pairing with frontend approval UX, display preference storage including Chromecast-version preference, access schedules, remote-access user policy overrides, concrete per-library access reporting, and HTTP/API-key/WebSocket request-time policy enforcement, but broader user policy semantics can still deepen.

### Collections, Lists, Playlists, Favorites

Jellyfin has collections in `CollectionController.cs`, playlists in `PlaylistsController.cs`, favorites/user data through `ItemsController.cs`, and collection/playlist models under `MediaBrowser.Model/Playlists/`.

pyrate has list CRUD, item add/remove, optimized items, user lists, liked lists, admin all, system lists, interactions, stats, collection routes backed by tagged user lists, and playlist routes with item ordering, playback queue generation, device play-queue dispatch, owner/admin metadata updates, and public share toggles in the existing list owner `backend/src/pyrate/api/v1/lists.py`; favorites status/toggle/list in `backend/src/pyrate/api/v1/favorites.py`; and UI in `frontend/src/pages/ListPage.vue`, `FavoritesPage.vue`, `AddToListDialog.vue`, and admin lists pages. Public playlist share URLs now resolve to `/playlists/:guid` without a login gate, load the ordered playlist endpoints, and expose a playlist play action that sends audio playlists into the persistent audio queue or opens the first playable video/game/book item with playlist query context so PlayPage can show ordered next/previous controls, auto-advance through playlist items, and persist playlist id/index context into viewing history plus playstate session summaries.

Status: **Partial**. Lists/favorites now cover much of the user workflow, collections have first-class API routes, and playlists have first-class API routes with ordering, queue generation, device play-queue dispatch, share toggles, owner/admin update semantics, share-route resolution, player UI entry points with ordered next/previous and auto-advance context, and playlist-aware viewing history/session summaries; deeper playlist session controls can still be deepened.

### Watch History, Resume, Playstate, Next Up

Jellyfin exposes resume items, user item data, and playstate updates in `ItemsController.cs` and `PlaystateController.cs`; TV next-up flows are represented by `TvShowsController.cs` and `MediaBrowser.Model/Querying/NextUpQuery.cs`.

pyrate has viewing history list/create/delete, HTTP playstate reporting with start/progress/pause/resume/stop/finish/seek events, optional device status updates, latest playstate session summaries, item-scoped `/api/viewing-history/{item}/playing`, `/progress`, and `/stopped` routes with tick conversion plus media-source/audio/subtitle hint preservation, continue watching, recently watched, deterministic next-up, and stats in `backend/src/pyrate/api/v1/viewing_history.py`; per-item user-data/favorite/like/playstate aggregation, native played/unplayed, favorite/unfavorite, and like/unlike commands, and selected audio/subtitle preference persistence in `backend/src/pyrate/api/v1/user_data.py`; player-side selected audio/subtitle preference save/restore in `frontend/src/composables/useMediaTracks.js` and initial saved-audio-track playback requests through `frontend/src/pages/PlayPage.vue`; media-detail like/unlike and watched/unwatched action buttons backed by native user-data state commands, per-item watch marking, show resume, and next/previous episode in `backend/src/pyrate/api/v1/media.py`; and UI in `frontend/src/components/ContinueWatching.vue`, `frontend/src/pages/ViewingHistoryPage.vue`, `frontend/src/composables/useViewingHistory.js`, and `useViewingProgress.js`.

Status: **Partial**. Resume/history, deterministic next-up, player-integrated selected track preferences, route-driven start position/media-source/audio/subtitle selection for playback commands, per-item likes/favorites/user-data with native state commands, richer cross-client playstate reporting, item-scoped playing/progress/stopped routes, latest playstate session summaries, and session-targeted play-command delivery are present, but the deepest session-integrated playstate semantics still need parity work.

### Search, Filtering, Genres, Suggestions, Recommendations

## Top Priorities

1. **Direct play/direct stream parity** - Highest daily-use impact; playback-info plus profile/device-aware play/seek requests, explicit client container/bitrate capability handling, protocol container/transcoding capability profiles, play/seek request media-source selection, selectable media-source listing, frontend source-aware quality switching, trickplay manifest hookup, built-in playback profiles, token-backed direct file playback, direct file URLs, direct-play fallback around blocked unnecessary transcodes, and direct-stream decisions now exist, but deeper DLNA/external-client negotiation around `backend/src/pyrate/api/v1/play.py` and `stream.py` still needs depth.
2. **Subtitle and audio management** - Metadata-backed and generic network subtitle provider search/download, OpenSubtitles-style search normalization and API-key-backed download-link resolution, LRCLIB-shaped lyrics normalization, text upload/content plus URL-backed subtitle proxying with player-track hookup, managed delete, fallback font settings, and player-persisted selected track preferences now exist; deepen additional provider integrations as needed.
3. **Manual metadata and artwork editing** - Audited manual metadata edits, metadata-backed identify/apply, live provider identify search, metadata-backed and live provider remote image search/select with language filtering, selected remote image proxying, normalized media/person external provider links, safe external-ID lookup, artwork upload/local serving, image transform descriptors, and packaged Pillow-backed uploaded/remote artwork transforms now exist; deepen provider-specific image semantics to close common library-correction workflows.
4. **Playstate/user-data contract** - Per-item user data now normalizes progress, played state, favorites, likes, native played/favorite/liked commands, player-integrated selected track preferences, route-driven start position/media-source/audio/subtitle playback-command selection, deterministic next-up, HTTP playstate/device status reporting, native item-scoped playing/progress/stopped routes, latest playstate session summaries, active device-session playback state/progress summaries, a native device session contract, and session-targeted play-command delivery; richer session-integrated playstate semantics still need a fuller pyrate-native contract.
5. **Playlists as playback objects** - Collections and playlists are route surfaces backed by the existing `lists.py`/`ListService` owner, with ordered playlist APIs, playlist queue generation, playlist-to-device play-queue dispatch, sharing, owner/admin controls, share-route resolution, frontend playlist play entry points, ordered next/previous plus auto-advance context, and playlist-aware viewing history/session summaries now present. Future playlist work must continue extending the list owner instead of creating separate playlist/collection services or copied route modules.
6. **Remote control/session commands** - Active session listing, HTTP/WebSocket device commands, stable device-id targeting, dedicated session messages, play-media/play-queue/play-command commands, browse commands, capability registration, session-user attach/detach, and playlist queue generation now exist; extend into pyrate's broader native session model and external client interoperability.
7. **Admin observability and backup** - API keys, activity/client logs, broad notification event catalogs with validated plugin-advertised event definitions, public/private system info, settings/database backup export/restore with guarded delete-missing controls, media manifests with copy/dry-run automation, task status history, run-level task inspection, install wizard configuration routes, Taskiq middleware callback logging, recommendation worker task events, reusable tracked-worker execution, and network runtime/proxy metadata now exist; executable plugin event hooks remain a deeper extensibility gap.
8. **Casting protocol support** - Manual cast target registration, pyrate-backed active-session discovery, opt-in DLNA SSDP discovery, opt-in Chromecast/AirPlay mDNS discovery, DLNA play/pause/stop/seek/status control with generated DIDL-Lite metadata, AirPlay HTTP play/pause/resume/stop/status control with play metadata fields, Chromecast DIAL/Eureka app launch/stop/status, Cast V2 media namespace play/pause/resume/stop/seek and queue-load support, receiver volume/mute, active media-session-id resolution, active media-status correlation, custom receiver app ids, protocol capability reporting with playback profiles/command lists, pyrate-backed command relay, and media-detail remote play initiation with profile/device-aware playback options now exist, but broader Chromecast app interoperability remains a user-visible living-room gap.
9. **Pre-merge integration audit (blocking)** - Before merging parity work, inspect the actual code for foreign-product naming, standalone adapter files, uppercase/non-pyrate route names, duplicate route systems, copied controller-shaped modules, or parallel services/models/schemas that should instead be integrated into pyrate's existing domain modules. New modules are allowed only when pyrate has no existing module/system for that domain; otherwise work must be folded into the native pyrate API/service/module with pyrate naming and route conventions. This gate must include source/test searches, frontend route-call searches, `backend/src/pyrate/api/router.py` ownership review, and a short written decision for each new backend API/service/model/schema file before merge. If the audit finds a duplicate, the merge is blocked until it is removed or integrated.
